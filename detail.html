Microsoft Entra ID アプリ登録 作業依頼書

Microsoft Graph API 連携のための OAuth アプリケーション登録手順

管理者様へ

本書は、申請者が開発・運用するアプリケーション（社内 AI アシスタント／ISMS 監査支援システム 等）を Microsoft 365 環境と連携させるため、対象テナント内に OAuth アプリケーション登録 を行っていただく作業手順を、画面操作レベルで記載したものです。

想定対応者
Microsoft Entra ID（旧 Azure AD）の グローバル管理者 または アプリケーション管理者 ロールを保有される方
※ Microsoft 365 の管理者画面（admin.microsoft.com）にサインインできて「Entra ID（または Azure AD）」のメニューが見える方であれば対応可能です。
想定所要時間
30〜45 分（本書を見ながら画面を操作する想定）
困った時のご連絡
作業中に画面の表記が本書と異なる、ボタンが見当たらない、エラーが出る等の場合は、自己判断で進めず作業をその時点で止めて、10 章記載の連絡先までご連絡ください（即日対応します）。

0. 用語と前提

用語説明
Microsoft Entra ID旧 Azure Active Directory（Azure AD）。Microsoft 365 のユーザー・認証基盤
アプリ登録 (App Registration)外部アプリケーションが Microsoft 365 のデータにアクセスするための「身分証」をテナント内に発行する操作
委任権限 (Delegated)アプリがサインインユーザー本人として API を叩く方式。ユーザーが持つ権限の範囲内でしか動かない
アプリ権限 (Application)アプリ自体に与えられる権限。ユーザー不在で動く（バッチ用途）。本案件では 使用しません
管理者同意 (Admin Consent)テナント全体に API 利用許可を与える管理者の確認操作
Client ID / Tenant IDアプリ登録完了後に発行される識別子（UUID）。申請者に通知いただく
スコープ (Scope)API のうち、どの操作を許可するかの粒度（例：Files.Read.All = 全ファイル読み取り）

本案件における原則

  • ✅ 委任権限のみ を使用（アプリ権限は不使用）
  • ✅ 読み取り (Read) 権限のみ（書き込み・削除は要求しません）
  • ✅ シングルテナント設定（対象テナント内でのみ利用可能・他社からはアクセス不可）
  • ✅ OAuth 2.0 Authorization Code Flow + PKCE（パブリッククライアント・クライアントシークレット不使用）

作業開始前の確認事項

以下を満たしていれば本書の手順を実施可能です。1 つでも該当しない場合は申請者にご連絡ください。

  • Microsoft 365 の管理者用アカウント（業務用メールアドレス）でサインインできる
  • そのアカウントが「グローバル管理者」または「アプリケーション管理者」ロールを持っている
    確認方法：admin.microsoft.com にサインイン → 右上のアカウントアイコン → 「自分のアカウント」→「ロール」欄を確認
  • 本書をご自身の画面で表示しながら、別タブで管理画面を操作できる環境がある
  • 作業中に申請者と連絡を取れる手段（メール・電話）がある

1. 作業概要（5 ステップ）

Step内容所要
1Entra ID 管理センターへアクセス約 1 分
2アプリ登録（名前・アカウント種類・リダイレクト URI）約 5 分
3API アクセス許可（スコープ）の追加10〜15 分

2. Step 1: Entra ID 管理センターへアクセス

① ブラウザを開くhttps://entra.microsoft.com
② サインイン対象テナントの グローバル管理者 または アプリケーション管理者 アカウントで
③ 左サイドメニュー「アプリの登録」をクリック（サイドバー直下にあります）
※見当たらない場合は「アプリケーション」を展開するとその中にあります
旧 UI の Azure Portal（https://portal.azure.com）からも同じ操作可能：
「Azure Active Directory」→「アプリの登録」
確認ポイント：上部に「+ 新規登録」ボタンが見えれば正しい画面です。

3. Step 2: アプリ登録

① 上部「+ 新規登録」をクリック「アプリケーションの登録」画面に遷移
② 名前（プロダクト名）-prod（例：athletie-prod / isms-audit-prod）
③ サポートされているアカウントの種類✅「この組織ディレクトリのみに含まれるアカウント（[対象テナント名] のみ - シングルテナント）」を選択
④ リダイレクト URI（プラットフォーム）「パブリッククライアント／ネイティブ（モバイルとデスクトップ）」
⑤ リダイレクト URI（URL）http://localhost:8400/callback（開発環境）
本番デプロイ後に更新依頼が改めて入る可能性があります
⑥ 「登録」ボタンクリック → アプリが作成され「概要」画面が開く
確認ポイント：「概要」画面に アプリケーション (クライアント) ID と ディレクトリ (テナント) ID が表示されれば OK。

4. Step 3: API アクセス許可（スコープ）の追加

登録されたアプリの画面で：

① 左メニュー「API のアクセス許可」をクリック
② デフォルト権限を確認Microsoft Graph / User.Read が既に入っている（保持）
③ 「+ アクセス許可の追加」クリック
④ 「Microsoft Graph」を選択縦に並んだ API から選ぶ
⑤ 「委任されたアクセス許可」を選択※「アプリケーションの許可」は選ばない
⑥ 検索ボックスに以下のスコープを 1 つずつ入力該当行のチェックボックスを ON
⑦ 全て選択し終わったら「アクセス許可の追加」⚠️ 押さずに閉じるとチェックが全て破棄されます（複数回に分けて追加しても可）
⚠️ 検索しても項目が出てこない場合：検索結果はカテゴリ見出しで折りたたまれて表示されます。フルネーム（例：Calendars.Read）ではなく ドットより前のみ（例：Calendars）で検索し、出てきた見出し行をクリックして展開してから該当項目を選択してください。Calendars.Read / People.Read / Presence.Read はこの挙動で見落としやすい項目です。

5. Step 4: 認証設定（パブリッククライアントフロー有効化）

① 左メニュー「Authentication (Preview)」をクリック（日本語表示の場合は「認証」）
② 開くのはリダイレクト URI 画面クリック直後は「プラットフォーム構成」→「モバイル アプリケーションとデスクトップ アプリケーション」の画面が開きます。http://localhost:8400/callback が登録されていることを確認
③ 「設定」タブへ切り替え⚠️ パブリッククライアントの設定は同じ画面にありません。ページ上部のタブから「設定」（英語表示では「Settings」）をクリック
④ ページ下部へスクロール「詳細設定」セクションまで移動
⑤ 「パブリック クライアント フローを許可する」トグルを はい（オン・青）に変更
⑥ 「保存」ページ上部の保存ボタンをクリック（新 UI では自動保存される場合あり）

5.1 補足：パブリッククライアントフローとは

クライアントシークレット（パスワード相当）を使わず、ブラウザでの OAuth 認証のみで動作する方式です。OAuth 2.0 + PKCE による標準的なセキュリティが担保されており、デスクトップアプリ・CLI ツール用途に推奨されています。

6. Step 5: 管理者同意の付与 + ID の控え

6.1 管理者同意の付与

① 左メニュー「API のアクセス許可」に戻る
② 「[対象テナント名] に管理者の同意を与えます」ボタンクリック
③ 確認ダイアログ「はい」を選択
④ 完了後全スコープの「状態」列が「[対象テナント名] に付与されました」（緑チェック）になることを確認
⚠️ 管理者同意なしの場合：ユーザーが初回ログイン時に 各人ごと に同意画面で OK する必要があり、UX が大幅に悪化します。本案件では管理者同意を付与いただく前提です。

6.2 Client ID / Tenant ID の控え

① 左メニュー「概要」をクリック
② 「基本」セクションの 2 つの値を控える以下の 2 項目を申請者にご返送ください

通知いただく情報：

項目控える値（UUID 形式）

※ Client ID / Tenant ID 単体では機密性は高くありませんが、組織の管理運用ルールに従ってください。

7. セキュリティ・運用上の留意事項

7.1 本アプリができること（権限内）

  • 委任権限のため、サインインしたユーザー本人がアクセスできる情報のみ取得します
  • ユーザーが見れないファイル・メッセージは取得できません
  • 書き込み・削除・送信は 一切できません（読み取りスコープのみ）

7.2 本アプリができないこと（権限外）

  • ❌ 他のユーザーのデータへの直接アクセス
  • ❌ ファイル・メールの編集・削除・新規作成
  • ❌ アカウント情報の変更
  • ❌ 管理者操作（ユーザー作成・権限変更等）

7.3 アクセストークンの取扱い

  • 取得したアクセストークンは クライアント PC のローカルファイル（暗号化済み）に保存します
  • サーバ側・第三者には送信されません
  • リフレッシュトークン有効期限：90 日間（業界標準）
  • ユーザーがサインアウト操作を行うとローカルキャッシュも破棄します

7.4 監査・透明性

  • Microsoft Entra ID の サインインログ から、本アプリによる API 呼び出しは全て記録されます
    管理センター →「サインインログ」→ アプリ名でフィルタ可能
  • 不審なアクセスがあれば即時アプリ登録を 無効化 いただくことで全 API アクセスを停止できます
  • 必要に応じて 条件付きアクセス（特定 IP・MFA 必須等）の設定も可能です

7.5 同意の撤回

完全削除アプリ登録画面で「削除」
一時停止アプリ登録画面で「非アクティブ化」
スコープ削減「API のアクセス許可」で個別スコープを削除
ユーザー単位の同意取り消し「エンタープライズアプリケーション」→ 該当アプリ →「アクセス許可」→ ユーザー個別

8. FAQ

クライアントシークレットを発行する必要はありますか？
いいえ、不要です。本案件はパブリッククライアント（PKCE）方式のため、シークレット発行は行いません。
スコープを一部だけ承認したいのですが？
可能です。ただし機能の一部が動作しなくなる可能性があります。申請者にご相談ください。例：Chat.Read を外す → 1 対 1 チャット閲覧機能が無効化／Mail.Read を外す → メール検索機能が無効化／Sites.Read.All を外す → SharePoint 横断検索が動作しません（本案件のコア機能）
アプリ登録には Microsoft 365 ライセンスが必要ですか？
いいえ、不要です。Entra ID Free でアプリ登録自体は可能です。ただし、本アプリを利用するエンドユーザー側には Microsoft 365 ライセンス（Teams／SharePoint／OneDrive 等のサービスにアクセスできるもの）が必要です。
既存の社内 SSO（Entra ID 連携）に影響しますか？
影響ありません。本アプリは独立した OAuth クライアントとして登録され、既存の SSO 構成・条件付きアクセスポリシー・アプリケーションプロキシ等とは独立して動作します。
リダイレクト URI の http://localhost:8400/callback はセキュリティ上問題ないですか？
問題ありません。OAuth 2.0 仕様で「ループバックアドレス」は例外的に HTTP が許可されており、デスクトップアプリの標準的な実装方式です（RFC 8252）。
条件付きアクセスの対象にできますか？
可能です。「エンタープライズアプリケーション」→ 該当アプリ →「条件付きアクセス」から設定可能です。MFA 必須・特定 IP のみ許可等を強制できます。
ログ収集対象にできますか？
可能です。Microsoft Entra ID の「サインインログ」「監査ログ」で本アプリの全アクティビティが取得できます。Microsoft Sentinel／Log Analytics へ転送して長期保管も可能です。

9. 作業完了後のチェックリスト

以下を全てチェックできれば作業完了です：

  • アプリ登録が完了し、「概要」画面に Client ID / Tenant ID が表示されている
  • サポートされているアカウントの種類が シングルテナント になっている
  • リダイレクト URI に http://localhost:8400/callback が パブリッククライアント として登録されている
  • 「パブリック クライアント フローを許可する」が はい になっている
  • 必要スコープ全てが 管理者同意付与済み（緑チェック） になっている
  • Client ID / Tenant ID を申請者指定の方法で通知した
